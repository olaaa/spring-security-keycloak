Это фрагмент конфигурации **OAuth2-клиента** (в связке Spring Security ↔ Keycloak). Он описывает **“регистрацию клиента”** — то есть *какое приложение* и *с какими параметрами* будет обращаться к Keycloak за авторизацией/токенами.

```yaml
registration:
  keycloak:
    client-id: springsecurity
    client-secret: XUhZtnkxB6hTsOvN5Pcblxvw2C1wBB8G
    scope: openid
```


### Что означает каждая строка

- `registration:`  
  Раздел “регистраций” OAuth2-клиентов. Можно иметь несколько клиентов (Google, GitHub, Keycloak и т.д.), и тут они перечисляются.

- `keycloak:`  
  Это **имя регистрации** (произвольный алиас), по которому Spring будет ссылаться на конкретного клиента. Например, в URL-ах логина/редиректа часто фигурирует именно это имя.

- `client-id: springsecurity`  
  **Идентификатор клиента** в Keycloak. Это публичное имя приложения, которое вы создали/настроили в админке Keycloak (в разделе Clients). По нему Keycloak понимает, *кто именно* запрашивает логин/токен.

- `client-secret: ...`  
  **Секрет клиента** — общий секрет между вашим приложением и Keycloak. Он используется, чтобы доказать, что запрос на токены делает именно доверенное приложение (актуально для “confidential client”).  
  Важно: это чувствительные данные, обычно их выносят в переменные окружения/секрет-хранилища, а не хардкодят в YAML.

- `scope: openid`  
  Запрашиваемые **права/области доступа**. `openid` означает, что используется **OpenID Connect**, и вы хотите получить “логин-поток” (ID Token) плюс базовую идентификацию пользователя.  
  Часто добавляют также `profile`, `email` и т.п., если нужны соответствующие claims.

### В двух словах “что делает этот блок”
Он говорит Spring Security: *“Для провайдера Keycloak используй клиента `springsecurity`, аутентифицируйся как confidential client с таким секретом и запрашивай минимум OIDC (`openid`).”*

# Resource Server
Этот кусок YAML включает режим **Resource Server** в Spring Security и говорит приложению: *«принимай запросы с `Authorization: Bearer <JWT>` и проверяй JWT-токены, доверяя конкретному issuer (выдавшей стороне)»*.

```yaml
spring:
  security:
    oauth2:
      resourceserver:
        jwt:
          issuer-uri: http://localhost:8080/realms/eselpo
```


## По строкам

- `spring.security.oauth2.resourceserver`  
  Включает конфигурацию **серверa ресурсов**. Это сценарий, когда ваше приложение **не логинит пользователя само**, а **защищает API/страницы** и пускает только с валидным access token.

- `jwt`  
  Уточняет, что токен — именно **JWT** (а не “opaque token”, который нужно интроспектить отдельным запросом).

- `issuer-uri: http://localhost:8080/realms/eselpo`  
  Это ключевое: **кто выдал токен** (Issuer).  
  Spring по этому адресу делает OIDC Discovery (по стандартному пути вида):

    - `http://localhost:8080/realms/eselpo/.well-known/openid-configuration`

  Из этого документа Spring автоматически узнает:
    - где брать публичные ключи (`jwks_uri`) для проверки подписи JWT,
    - какие endpoint’ы относятся к этому реалму,
    - и будет проверять, что в токене поле `iss` совпадает с этим `issuer-uri`.

## Что происходит при запросе

Когда приходит запрос с заголовком:

```
Authorization: Bearer <jwt>
```


Spring Security:
1. достаёт JWT,
2. проверяет подпись (по ключам из JWKS),
3. проверяет, что `iss` совпадает с указанным `issuer-uri`,
4. проверяет сроки (`exp`, `nbf`) и базовые требования,
5. создаёт `Authentication` и пускает дальше, если всё ок.

## Частые нюансы

- **Issuer должен совпадать один-в-один** (включая протокол `http/https`, порт, хвост `/realms/...`). Иначе будет ошибка “Invalid issuer”.
- Это **настройка именно для проверки входящих токенов**. Для “войти через браузер” (Authorization Code flow) используется другая ветка (`oauth2.client...`), а тут — “принять bearer token и валидировать”.
